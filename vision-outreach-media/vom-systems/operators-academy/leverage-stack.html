Lesson 01~8 min

The Leverage Ladder

Leverage is the amount of output you get from one unit of your attention. An operator with no leverage does every task with their own hands, every time. An operator with high leverage does a task once, then never spends full attention on it again. The whole job is climbing from the first state to the second — deliberately, one task at a time.

There are four layers you can move a task into, and they run from cheapest and most flexible to richest and most expensive. Learn them as a ladder, because that ordering is the single most useful decision rule you will carry into every other VOM system.

01

Prompts & Context

A reusable prompt, a saved instruction, a project context file the model reads before it works. You write the words once and paste — or point — the model at them again and again.

Reach first — one-off & still-changing work
02

Skills

A named, described procedure the model loads on demand — instructions plus any scripts or reference files it needs. The same steps run the same way every time, and the description triggers it automatically.

Reach when the steps stop changing
03

Scheduled Tasks

A skill or prompt that fires on a clock instead of waiting for you to start it. The morning brief, the weekly report, the Monday monitor — they run whether or not you remember.

Reach when the work is on a clock
04

Agents & Agent Teams

Autonomous, multi-step work: an agent that plans, uses tools, branches on what it finds, and hands sub-tasks to other agents in parallel. The most capable layer — and the most expensive per run.

Reach last — when judgment can't be scripted
← cheaper · more flexible · less capablemore capable · pricier →

The one rule that governs the ladder

Reach for the cheapest layer that fully holds the task, and climb only when the layer below genuinely can't. Most operators do the opposite — they get excited about agents and reach for Layer 4 to do a Layer 1 job. That is how you end up paying premium prices and waiting on a slow, over-powered pipeline to do something a saved prompt did in one shot.

Read the ladder the other direction too. If you find yourself doing the same thing by hand for the third time, you are sitting one rung too low — that is your signal to climb. The ladder is not a place you settle; it's a direction you keep pushing each task upward along, until the marginal cost of doing it again is close to nothing.

The mental model Same task, four homes. A task doesn't belong to a layer forever. It starts as a prompt, earns its way into a skill once it's stable, gets scheduled once it's routine, and only becomes an agent job if it needs judgment you can't write down. Moving a task up the ladder is the core act of operating with leverage.

You've written the same three-paragraph outreach email, tweaked per prospect, about four times this month. Where does this task belong right now?

Layer 2. Four repetitions with a stable structure is the classic "promote it to a skill" signal — you've earned near-free reuse. An agent (Layer 4) is over-powered and expensive for a templated email; staying at Layer 1 leaves real leverage on the table.

Lesson 02~7 min

The Operator's Loop: Audit → Optimize → Automate

The ladder tells you where a task should live. The loop tells you how to move it there without breaking it. It's four moves, and the order is not optional — skip a step and you automate a mess.

1
Audit — do it once by hand

Run the task manually and watch yourself do it.

Every decision you make, every input you go looking for, every place you pause to think — write it down. You cannot package a process you haven't actually seen. The goal of this pass is a plain-language list of the real steps, including the judgment calls you make on autopilot.

2
Optimize — fix the steps

Cut, reorder, and standardize before you package anything.

Remove steps that don't earn their place. Nail down the inputs (same shape every time) and the outputs (a defined format). Replace "I just kind of know" with an explicit rule. A process that's ambiguous to you will be ambiguous to a skill, a schedule, or an agent — and they can't ask a colleague.

3
Package — make it repeatable

Turn the clean procedure into a skill.

Now it's worth writing down permanently: a description that says what it does and when to use it, the ordered steps, and any reference files or scripts it leans on. This is the moment a task stops living in your head and starts living in a system that anyone — or any agent — can invoke.

4
Automate — remove yourself

Schedule it, or hand it to an agent.

Once the packaged procedure runs cleanly under supervision, take your hands off. Put it on a clock if it's recurring, or delegate it to an agent if it needs to branch and use tools. You only reach this step after the process is stable — automation is an amplifier, and it amplifies whatever you point it at.

The expensive mistake Never automate a mess. Automating a bad process doesn't fix it — it just produces bad output faster and more often, and now nobody's watching. The loop's order exists to stop exactly this. Optimize before you package; package before you automate.

Notice how the loop maps onto the ladder: Audit and Optimize happen while the task still lives at Layer 1 (prompts and context). Package promotes it to Layer 2 (a skill). Automate pushes it to Layer 3 or 4. The loop is the act of climbing — done responsibly.

And it's a loop, not a line. When the automated version drifts or the world changes, you drop back to Audit, watch the new reality, and climb again. Good operators run this quietly and constantly, on one small task at a time, rather than trying to automate everything at once.

Your weekly client report takes an hour and involves a few "it depends" judgment calls you make from memory. What's the mistake to avoid?

Jumping to automation too early. Those "it depends" calls are exactly the ambiguity you must resolve in the Optimize step. Schedule it while they're still vibes-based and you'll get confidently wrong reports every week, unwatched. Make the rules explicit first, then climb.

Lesson 03~7 min

Cost as Leverage

Leverage isn't only about your time — it's about the cost of the work itself. Once a task runs on a machine, the question becomes: how cheaply can this run every single time it fires? The operator's instinct is to push each task down to the cheapest tier that still does it well, so the marginal cost of doing it once more stays close to zero.

There's a cost ladder inside the automation, running cheapest to priciest:

TierMarginal costUse it for
Code≈ freeAnything deterministic — parsing, formatting, math, date logic, moving files, string matching. Don't pay a model to do what a script does perfectly every time.
Cached contextfraction of fullReusing a large, stable prefix — a long system prompt, a knowledge base, a style guide — across many calls. Cache it once, pay a sliver on each reuse.
Cheap-tier modellowClassification, extraction, routing, tagging, first-draft text. Fast, small models handle the high-volume, low-ambiguity middle of most pipelines.
Premium modelhighestGenuinely hard reasoning — ambiguous judgment, architecture, nuanced writing, the load-bearing decision a whole pipeline hinges on. Spend here on purpose, not by default.

Route the work, don't run it all at the top

A well-built system almost never uses one tier. It routes: code does the mechanical parts, cheap-tier models chew through the bulk classification and drafting, cached context carries the shared background, and the premium model is reserved for the one or two steps that actually need frontier judgment. The art is drawing those lines correctly — pushing everything you can downward without breaking quality.

Play it out at scale. A task that costs a few cents at the premium tier feels trivial once. Fire it ten thousand times a month on a schedule and the tier you chose is the difference between a rounding error and a real bill. Keeping the marginal task near-free is what makes automation worth building at all — leverage that costs a lot per use isn't leverage, it's a subscription to your own process.

The routing instinct Code > cached > cheap-tier > premium. Ask of every step: could the tier below do this acceptably? Walk down until the answer is honestly no, and stop there. That's the cheapest correct home for the step.

A pipeline runs 8,000 times a month. One step reformats a date and strips whitespace from a name. Where should that step run?

Code. Reformatting a date and trimming whitespace is deterministic — a script gets it right every time for ≈ free. Paying any model 8,000 times a month for what a few lines of code do perfectly is exactly the leak this lesson exists to close.

Lesson 04~9 min

Worked Examples You Can Lift

Principles are cheap; patterns you can copy are the real deliverable. Here are three you can lift straight into your own operation — one per layer where the craft actually lives. Read what makes each one good, then adapt the wording to your work.

A. A skill description that actually triggers

A skill only helps if it fires at the right moment. The description is the trigger — the model reads it to decide whether to load the skill. Write it for retrieval: say plainly what it does, when to use it, and the words a person would naturally use to ask.

✕ Vague — won't fire reliably
"Helps with client reports."

No trigger words, no timing, no scope. The model can't tell a weekly performance report from a bug report, so it loads at the wrong time or not at all.
✓ Specific — fires on the real request
"Generate the weekly client performance report from that client's channel scores. Use when the operator asks to 'run the weekly report', 'send the Monday update', or prep a client's weekly numbers. Pulls the latest scores, writes the summary, and formats it for email."
Copy-readyweekly-client-report — SKILL.md front matter
---
name: weekly-client-report
description: Generate a client's weekly performance report from their
  latest channel scores. Use when the operator asks to "run the
  weekly report", "send the Monday update", or prep a client's
  weekly numbers. Pulls latest scores, writes the plain-language
  summary, and formats it for email.
---

# Steps
1. Load the client's latest scores (last 7 days) from the store.
2. Compute deltas vs. the prior week for each channel.
3. Write a 3-part summary: wins · watch-items · one next step.
4. Format with the house email template in ./assets/email.html
5. Return as a draft for the operator to review — never auto-send.
Why this is good Trigger phrases + a defined output + a human gate. The description names how people actually ask, the steps standardize the output, and step 5 keeps a person between the machine and the client. Notice it packages a process you'd have audited and optimized first (Lesson 02).

B. A scheduled task, fully specified

A schedule is only as good as what it runs and where the output lands. Specify all four: when it fires, what it runs, where the result goes, and what happens on failure. Leave any one vague and you get silent gaps.

Copy-readyscheduled-task — configuration
name:        monday-client-updates
schedule:    every Monday at 07:00 (operator's timezone)
runs:        skill: weekly-client-report   # the packaged procedure
for_each:    client in active_clients       # loop, one report each
model:       cheap-tier                     # drafting is not premium work
output:      draft in operator's review queue # NOT auto-sent
on_success:  notify operator: "12 drafts ready to review"
on_failure:  retry once, then alert operator with the error
note:        operator reviews + sends by 09:00. Human stays in the loop.
Don't skip failure handling A schedule with no failure path is a trap. The one week the data source is down, a silent task produces nothing and nobody notices until a client asks where their report is. on_failure is not optional polish — it's the difference between a system you can trust unattended and one you can't.

C. An agent hand-off that doesn't need a follow-up

When an orchestrator hands work to a subagent, the subagent starts cold — it has none of your context. A good hand-off is completely self-contained: goal, the context it needs, hard constraints, what "done" looks like, and the exact return format. Get this right and you can run subagents in parallel without babysitting; get it wrong and you spend more time correcting than the delegation saved.

Copy-readyorchestrator → subagent — hand-off brief
# HAND-OFF BRIEF  (orchestrator → research subagent)

GOAL:       Assess one prospect's public digital presence and
            return a channel-by-channel scorecard.

CONTEXT:    Prospect = "Riverside Community Church", Amersfoort.
            We score 8 channels on the house rubric (v3).
            You have web-search + the scoring rubric tool.

CONSTRAINTS:
            • Use only public sources — no login-gated pages.
            • Do not contact the prospect or submit any form.
            • Cap at ~15 minutes of research; note gaps, don't guess.

DONE MEANS: All 8 channels scored 0–100 with a one-line reason
            each, plus a 2-sentence overall read.

RETURN AS:  JSON: { channel: {score, reason} } + "summary".
            No prose outside those fields — the orchestrator parses it.
The pattern to internalize Goal · Context · Constraints · Done-criteria · Return format. Every strong hand-off has all five. The return-format line is the one operators forget — pinning it down is what lets the orchestrator combine many subagents' work automatically instead of re-reading each one by hand.

A subagent keeps returning slightly-different, hard-to-combine results across runs. Which part of the hand-off is most likely missing?

The return format. Inconsistent, hard-to-merge output is the signature of an unspecified return shape. Define the exact structure (the JSON contract above) and every run comes back the same way — no premium upgrade required.

Lesson 05~4 min

Assemble the Stack

You now hold the whole model. The ladder tells you where a task should live; the loop moves it there safely; cost thinking keeps it near-free once it runs. Put together, they're a single working habit you can apply to any process in front of you — which is exactly what every other product in the VOM house is built on top of.

Here's the whole module as one decision path, to run on your next real task:

  • Spot the repeat. You're doing something by hand for the third time — that's the signal to climb.
  • Audit & optimize. Do it once more deliberately, write down the real steps, and make the ambiguous parts explicit.
  • Package it. Promote the clean procedure to a skill with a description that triggers and an output that's defined.
  • Automate at the right cost. Put it on a clock or hand it to an agent — and route each step to the cheapest tier that still does it well.
  • Keep a human gate wherever the output touches a client, and a failure path wherever it runs unattended.

That's the leverage the rest of the house depends on. Learn it here, and every other system — the scans, the reports, the launch kits — stops looking like separate products and starts looking like the same four moves, stacked.

You've packaged a report skill and want to schedule it to run for every client, unattended, overnight. What's the last thing to lock in before you flip it on?

The failure path and human gate. Unattended + client-facing is exactly where silent failures and unreviewed output bite. Premium-everything (a) just burns money; "ready by definition" (b) ignores Lesson 04. The safeguards are the last, non-negotiable step.
