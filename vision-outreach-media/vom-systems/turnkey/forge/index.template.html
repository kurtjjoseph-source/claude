Two artifacts, two audiences

The decision record and the build order are different documents. Conflating them is what forces a person to stand in the middle of every build, translating.

turnkey/blueprint.md

The decision record

Written for a person. It argues: this is a church, so it needs giving and a sermon archive; here is why WordPress wins; revisit this if they hire staff.

Right shape for a decision. Wrong shape for a machine.

turnkey/platform-spec.json · apb/1

The build order

Written for a builder. Every question it could ask is already answered — which modules, which pages, what each page says, which records exist on day one, which rails are live, where it deploys, and what must be true afterwards.

Nothing else is consulted during a build.

forge

The runner

Reads the spec and does the work. It refuses an unready spec rather than producing a half-decided platform, and it refuses to publish without a prior logged authorization.

Every run is streamed, checked, receipted and replayable.

Archetype platforms

Both are compositions over one general module-based platform — the same runtime, the same renderer, the same section vocabulary. They differ only in what they compose, which is why a third archetype is a data change rather than a project, and why a platform can be named, composed and launched in minutes.

What keeps an unattended build honest

Removing the person from the build cannot mean removing the guarantees. These are mechanical, not aspirational — each one can refuse a run.

✓It will not run an unready spec

If the org type was guessed, or a page would ship a literal {business}, the run refuses before it writes a file.

✓It will not publish without a prior YES

Turnkey's rule is a logged consent that existed before the action. An unattended runner cannot ask mid-run, so the YES is granted once, up front, scoped to the whole run — one hash-chained line, and the spec carries its reference. No authorization, and every public target is refused.

✓It reports what happened

A deploy with no credentials is a failed stage with the reason attached, never a quiet success. The smoke stage fetches the real URL: "deployed" is a measurement, not a claim.

✓It never holds a credential

Rails without keys are built and clearly labelled in the interface — see the giving block on the church demo. They start working when the operator supplies the keys, which the builder never sees.

✓It checks its own work

Every check the spec declared is run against what was actually written — pages present, links resolving, no placeholder surviving, the modules an archetype insists on being there. A failed check stops the run before deploy.

✓It is reproducible

The spec carries a fingerprint of its own contents; the build records the fingerprint it built. "What is deployed" is a question with an answer, and an edited spec fails before it runs.

Running one

A business can be named, composed and launched in a single command.

# name a business — folder, blueprint, spec and build, in one go python3 turnkey.py forge --new "Bethel Chapel" \ --org-type church --city Amersfoort \ --about "A church that gathers every Sunday." \ --target local --watch # see what each forge builds, before any launch exists python3 turnkey.py archetypes # compile the build order from an existing launch, and inspect it python3 turnkey.py spec "<business folder>" --target vercel --save # authorize one unattended run, then let it go all the way to a public URL python3 turnkey.py forge "<business folder>" --target vercel \ --authorize-unattended --actor VOM --channel "operator console" --watch
